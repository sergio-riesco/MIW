Filtro Game Boy con WebAssembly

Imágenes

El filtro busca, para cada píxel, el color más cercano de los cuatro de la paleta de la Game Boy y lo sustituye. Sea cual sea la resolución elegida, la salida mide exactamente lo mismo que la imagen de entrada, y el navegador la muestra al tamaño que le corresponda.

WebAssembly contra JavaScript

Los dos resultados salen del mismo algoritmo: uno escrito a mano en WebAssembly (filtroGB.wat) y el otro en JavaScript puro. filtroGB-js.js es una traducción literal del .wat, con la misma paleta, la misma búsqueda del color más cercano y el mismo bucle de píxeles. Así lo único que cambia es dónde se ejecuta el código.

Cada implementación se ejecuta durante unos 60 ms, y como no tardan lo mismo, cada una repite el filtro un número distinto de veces. La columna que se puede comparar es Por pasada: el tiempo que tarda el filtro en procesar la imagen una vez. La más rápida aparece en verde. Los números cambian según el navegador y la máquina.

Por qué la diferencia no es mayor

Este filtro es un caso en el que el motor de JavaScript lo hace casi tan bien como WebAssembly: V8 compila los bucles sobre TypedArray a código máquina muy eficiente, así que las dos versiones acaban ejecutando instrucciones parecidas.

Además, WebAssembly tiene un coste que JavaScript no tiene: la imagen tiene que entrar y salir de la memoria lineal del módulo. Con la imagen actual se copian 0 KB en cada pasada solo para poder filtrar.

WebAssembly destaca cuando el JavaScript no se puede optimizar (funciones enormes o con tipos que cambian), cuando el trabajo por píxel es mucho más pesado, cuando se usan instrucciones SIMD, que JavaScript no tiene, o cuando el motor no dispone de compilador JIT. También ofrece un rendimiento más predecible: no hay pausas del recolector de basura ni fases de calentamiento.
