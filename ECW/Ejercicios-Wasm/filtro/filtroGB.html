WASM contra JavaScript

Los dos resultados salen de ejecutar el mismo algoritmo: uno compilado a WebAssembly y el otro en JavaScript puro. filtroGB-js.js es una traducción literal del .wat, con la misma paleta, la misma búsqueda del color más cercano y el mismo bucle de píxeles. Los tres canvas se dibujan a la vez y con el mismo tamaño, así que lo único que cambia es dónde se ejecuta el código.

Cada implementación se mide durante unos 60 ms, pero como el WASM es mucho más rápido cada una repite el filtro un número distinto de veces. La columna Por pasada es la que se puede comparar, porque es el tiempo que tarda el filtro en procesar una imagen. Los números cambian según el navegador y la máquina.

Por qué la diferencia es pequeña

Es normal que los dos tiempos estén parejos, y no es que el WASM esté explicando mal. Este filtro es justo el caso donde el motor de JavaScript ya lo hace casi tan bien como WebAssembly: V8 compila este tipo de bucles sobre TypedArray a código máquina muy eficientemente, así que las dos versiones acaban ejecutando instrucciones parecidas.

Además WASM carga con un coste que JavaScript no tiene: la imagen tiene que entrar y salir de la memoria lineal, y solo copiarla ya son cientos de kilobytes. En una imagen de 320 × 214 son unos 340 KB de memoria que se mueven solo para poder filtrar.

WebAssembly destaca de verdad cuando el JavaScript no se puede optimizar: funciones enormes, puntos de llamada que cambian de tipo, o un runtime sin JIT. También cuando el trabajo por píxel es mucho más pesado o cuando se pueden usar las instrucciones SIMD de WebAssembly, que en JavaScript no existen. Y cuando hay muchísimas llamadas pequeñas a cruzar la frontera entre los dos mundos.
